## Три модели работы вдвоём

| Модель | Как работает | Плюсы | Минусы | Когда |
|---|---|---|---|---|
| **A. Только Team Create** | оба открывают одну игру в Studio и правят вместе | проще всего, мгновенная синхронизация | слабая история/ревью, трудно использовать ИИ-агентов, риск «перетереть» | первые дни, прототип, билдеры |
| **B. Git + Rojo для кода, Team Create для сцены (рекомендуется)** | код — файлы в GitHub; сцена/объекты — в Team Create | ревью, CI, ИИ-агент работает с файлами, откат | нужно освоить инструменты | почти любые проекты |
| **C. Всё в Git (код + сцена через .rbxl/.rbxm/.model.json)** | сцена тоже в файлах | полная воспроизводимость | двоичные файлы не сливаются, конфликты | специфические случаи, малые карты |

**Рекомендация:** модель B.

## Team Create: основы

- Включается в Studio: **Home → Team Create** (игра должна быть опубликована).
- Приглашение людей: **Creator Hub → ваш Experience → Permissions / Collaborators** (или кнопка Team Create в Studio). Для игр под **группой** — права по ролям группы.
- Правки видны всем в реальном времени: перемещения частей, свойства.
- Скрипты в Team Create редактируются через механизм **черновиков (drafts)**: правки в редакторе фиксируются (commit) и не мешают остальным до применения — не забывайте закрывать/коммитить.
- Откат: **Version History** (Studio / Creator Hub).
- Права: у каждого участника уровень доступа (просмотр, редактирование, администрирование) — давайте минимально необходимое.

:::warn Бэкап обязателен
Team Create — не бэкап. Регулярно (раз в день/после крупных правок) делайте **File → Save to File As… (.rbxl)** в папку `backups/` (вне Git, либо Git LFS) и/или публикуйте в отдельный `Dev (backup)` плейс. Случайное удаление объектов и перетирание — частая причина потерь.
:::

## Git + Rojo: цикл разработчика

```bash
git clone git@github.com:you/mygame.git
cd mygame
rokit install        # установить инструменты из rokit.toml
wally install        # пакеты
rojo serve           # синхронизация в Studio
```

Ветки (простой GitHub Flow):

```bash
git checkout -b feat/daily-reward
# ... работа (с ИИ-агентом) ...
stylua src && selene src
git add -A
git commit -m "feat: ежедневная награда (сервер + клиент)"
git push -u origin feat/daily-reward
# открыть Pull Request на GitHub, напарник ревьюит, merge в main
```

Правила:
1. **main всегда рабочий.** Прямой push в main запрещён (защита ветки в настройках репозитория: Require pull request, Require status checks).
2. **Одна ветка — одна задача.** Короткоживущие ветки (1–3 дня).
3. **Мелкие PR** (до 300–400 строк) — их реально проверить.
4. **Ревью напарника**: на сервере/деньгах — внимательно по чек-листу безопасности.
5. **Squash merge** — аккуратная история, один коммит на фичу.
6. **Сообщения коммитов** в одном стиле: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`.

## Как Rojo переносит код в игру

```text
src/server/Main.server.luau   ──► ServerScriptService.Server.Main (Script)
src/shared/Config.luau        ──► ReplicatedStorage.Shared.Config (ModuleScript)
src/client/UI/init.luau       ──► StarterPlayerScripts.Client.UI (ModuleScript + дети)
```

В **Studio** вы нажимаете Connect → любой сохранённый файл моментально появляется в игре. Это «живая синхронизация» (только для разработки). В **продакшн** код попадает через сборку: `rojo build -o build/game.rbxl` → публикация (вручную или CI).

:::note Две реальности
Когда Rojo подключён, код в Studio — «зеркало» файлов. Не правьте скрипты в Studio, правьте файлы. Правки сцены (части, UI-объекты, свойства) Rojo не затронет, если используется `$ignoreUnknownInstances` и вы не описали их в проекте.
:::

## Как сцена и код живут вместе

Типичный вариант:
1. **Карта и объекты** собираются в Studio (Team Create) в Dev-плейсе.
2. **Скрипты** приходят из Git через Rojo (или сборкой). В объектах сцены — только данные/атрибуты/теги и `ProximityPrompt` и т.п., а логика — в скриптах из репозитория, привязанных по тегам (`CollectionService`).
3. **Публикация**: из Studio (если не CI) — «Publish to Roblox» после `rojo serve` (код уже в игре) **или** сборка `game.rbxl` с кодом + карта.

Две распространённые схемы публикации:
- **Схема 1 (проще):** карта хранится в Studio-плейсе, код подключается Rojo при работе; публикует релиз-менеджер из Studio кнопкой «Publish». Минус — публикация вручную.
- **Схема 2 (CI):** карту экспортируют в `map.rbxl` (или `.rbxm`) и хранят в репозитории (Git LFS) → `rojo build` собирает финальный `game.rbxl` из `map` + код → Open Cloud публикует. Плюс — воспроизводимость; минус — двоичные конфликты.

## Конфликты и как их избегать

| Тип | Причина | Решение |
|---|---|---|
| Git-конфликт в коде | оба правили один файл | мелкие PR, частые `git pull --rebase`, договорённость о владельцах файлов; решать вручную в редакторе/с ИИ |
| Конфликт `.rbxl` | двоичный файл | не коммитить правки карты параллельно; один человек владеет «картой» в момент времени |
| Перетёртая сцена | оба правят в Team Create | зоны ответственности (кто какой район карты), Version History |
| Расхождение «код в Studio vs Git» | кто-то правил скрипты в Studio | правило: код только из Git; пересинхронизация Rojo |
| «Работает у меня» | разные версии инструментов | `rokit.toml` / `wally.lock` в Git |

## Обновления: что происходит у игроков

1. Вы публикуете новую версию.
2. **Новые серверы** запускаются уже на ней; **старые** продолжают работать на предыдущей, пока не закроются (или вы не перезапустите).
3. Поэтому изменения должны быть **обратно-совместимыми**: старый сервер и новый сервер должны «жить рядом» (общий DataStore!). Миграции схемы — аддитивные (добавляем поля, не переименовываем без перехода).
4. Крупные обновления: заранее предупредите игроков (MessagingService), затем принудительно перезапустите серверы.
5. Опасные фичи включайте **через флаг** (атрибут/DataStore), чтобы выключить без релиза.

```lua
local types = {}
```

```lua
local types = {"feat", "fix", "docs", "chore"}
```

::::task mid Сравнение версий (чистый Lua)
Для проверки обратной совместимости схемы данных напишите `isCompatible(serverVersion, dataVersion)`: версии — целые числа. Новый сервер (`serverVersion`) может читать данные своей версии и более старых (миграция вперёд), но **не** более новых — вернуть `false`, чтобы старый сервер не затёр данные нового формата.

:::starter
```lua
local function isCompatible(serverVersion, dataVersion)
end
```
:::
:::test
```lua
assert(isCompatible(3, 3) == true)
assert(isCompatible(3, 1) == true)
assert(isCompatible(2, 3) == false)
```
:::
:::answer
```lua
local function isCompatible(serverVersion, dataVersion)
  return dataVersion <= serverVersion
end
```
Если старый сервер загрузил данные новой версии, он должен отказаться сохранять их (или перевести игрока на новый сервер).
:::
::::
