## Типовая пара

| Роль | Кто | Основные задачи |
|---|---|---|
| **Скриптер (инженер)** | человек A (+ ИИ-агент) | код, архитектура, сохранения, экономика, интеграции, релизы |
| **Билдер/дизайнер** | человек B (+ ИИ-ассистенты для арта/текста) | карта, UI-макеты, модели, иконки, звук, баланс, контент, сообщество |

Вариации: «оба кодят, один отвечает за геймдизайн и продвижение». Главное — **у каждой зоны один ответственный** (owner), а второй — ревьюер/помощник.

:::tip Разделите «кто чем владеет»
Скриптер владеет `src/` (репозиторий), билдер — картой (`Workspace`, UI-ассеты, модели). Конфликты возникают там, где оба правят одно и то же без договорённости.
:::

## Что нужно договориться в первый день (1 страница)

1. **Видение игры** одним абзацем + 3 главных цикла (core loop, прогрессия, монетизация).
2. **Роли и зоны владения** (см. выше).
3. **Инструменты:** Roblox Group (владелец игры), GitHub (код), Discord (общение), Notion/Trello/GitHub Projects (задачи).
4. **Правила изменений:** кто и что имеет право публиковать в продакшн (в идеале — один человек, «релиз-менеджер»).
5. **Деньги и права:** доли, как делится доход, что будет, если кто-то уйдёт (см. [[team-04-money-rights]]).
6. **Формат связи:** ежедневный короткий созвон/сообщение, еженедельная планёрка.

## Ритм работы (простая Agile-версия)

| Когда | Что | Длительность |
|---|---|---|
| Ежедневно | «Сегодня / вчера / блокеры» в чате (3 строки) | 5 мин |
| Раз в неделю | Планёрка: итоги → метрики → задачи на неделю | 30–45 мин |
| Раз в 1–2 недели | **Релиз** обновления (контент + фиксы), пост в сообществе | — |
| Раз в месяц | Ретро + пересмотр стратегии (что работает/нет) | 45 мин |

Доска задач из 4 колонок достаточно: **Backlog → In progress → Review → Done**. Правило: не более 2 задач «в работе» на человека.

## Жизненный цикл фичи

```text
Идея → Мини-ТЗ (5 строк) → Ветка в Git → Код (ИИ-агент) → Автопроверки (CI) → PR → Ревью напарника
     → Playtest в Studio (Local Server) → Merge в main → Релиз в Staging → Релиз в Production → Метрики (через 1–3 дня)
```

Мини-ТЗ (шаблон):

```markdown
**Фича:** Ежедневная награда
**Зачем:** повысить D7 (метрика: D7 retention)
**Как работает:** раз в 24 ч игрок получает награду по таблице на 7 дней; пропуск сбрасывает серию.
**Сервер:** DailyRewardService (проверка времени по серверу, DataStore)
**Клиент:** окно награды, анимация, звук
**Критерии готовности:** сохранение при перезаходе; нельзя получить дважды; тест на телефоне.
**Риски:** смена часового пояса/читерство со временем.
```

## Как разделить работу без конфликтов

| Зона | Владелец | Где хранится | Правило |
|---|---|---|---|
| Код (серверный и клиентский) | Скриптер | Git (`src/`) | только через PR |
| Конфиги баланса (`*.config.luau`, JSON) | Оба | Git | небольшие PR, ревью напарника |
| Карта, объекты, UI-макет в Explorer | Билдер | Team Create / `.rbxl` | не править скрипты внутри объектов (код — только из Git) |
| Модели/ассеты | Билдер | Creator Hub + `.rbxm`/Studio | давать понятные имена и теги |
| Тексты, локализация | Билдер + ИИ | таблицы в Git | единая таблица ключей |
| Метрики, решения | Оба | Doc/Notion | еженедельный обзор |

:::danger Не держите код в двух местах
Если скрипты правятся и в Studio (Team Create), и в Git — они разъедутся. Выберите **один источник истины для кода** (Git + Rojo), а Studio используйте для карты и объектов. Подробности — следующая страница.
:::

## Коммуникация

- **Асинхронно по умолчанию:** сообщения в чате с контекстом («что сделал, что нужно от тебя, к какому сроку»).
- **Видео/голос** — когда обсуждаете дизайн и решения.
- **Решения записывайте** в `docs/decisions.md` (дата, решение, причина). Через месяц это спасает от споров.
- **Конфликт мнений:** тест > мнение. Запустите эксперимент (A/B на части игроков) или плейтест.

## Работа с ИИ в паре

- Единый `AGENTS.md` — оба пользуются одними правилами.
- Разделите «кто какими ИИ-подписками платит»: проще, если у скриптера основной ИИ-инструмент, а у билдера — генераторы арта.
- Промпты и стайлгайды — в репозитории (`docs/prompts/`), чтобы результат был воспроизводим.
- PR от ИИ — всегда с ревью человека.

## Антипаттерны командной работы

| Плохо | Последствие | Лучше |
|---|---|---|
| Оба публикуют в продакшн когда хотят | сломанные релизы | один релиз-менеджер + чек-лист |
| «Скажу устно» | потеря решений | запись в чате/доке |
| Правки сцены и кода без истории | не откатить | Git + регулярные `.rbxl`-бэкапы |
| Никто не смотрит чужой код | баги на проде | PR с ревью (даже 5 минут) |
| Нет метрик | решения «на ощущениях» | еженедельный обзор Creator Hub |
| Нет договорённостей о деньгах | ссора после успеха | письменное соглашение заранее |

## Задания

::::task easy План на неделю
Составьте для вашей пары на ближайшую неделю: 3 задачи скриптера, 3 задачи билдера, 1 общая цель (метрика). Проверьте, что у каждой задачи есть владелец и критерий готовности.

:::answer
Пример:
- **Цель недели:** поднять D1 retention с 20% до 25%.
- Скриптер: (1) DailyRewardService + сохранение — критерий: награда не выдаётся дважды; (2) Tutorial-подсказки — критерий: 80% новых игроков доходят до первой покупки; (3) Автосохранение 120 с — критерий: нет потери данных при выходе.
- Билдер: (1) Новая стартовая зона — критерий: тест на телефоне ≥ 30 FPS; (2) UI окна награды — критерий: кнопки ≥ 44 px; (3) 12 иконок предметов — единый стайлгайд.
:::

::::task mid Планировщик релиза (чистый Lua)
Напишите `nextRelease(lastRelease, intervalDays)`: даты — строки `YYYY-MM-DD`. Верните дату следующего релиза через `intervalDays` дней в том же формате. (Подсказка: `os.time{year=..., month=..., day=..., hour=12}` и `os.date("%Y-%m-%d", t)`.)

:::starter
```lua
local function nextRelease(lastRelease, intervalDays)
end
```
:::
:::test
```lua
assert(nextRelease("2026-10-19", 14) == "2026-11-02")
assert(nextRelease("2026-12-25", 10) == "2027-01-04")
assert(nextRelease("2028-02-27", 3) == "2028-03-01")
```
:::
:::answer
```lua
local function nextRelease(lastRelease, intervalDays)
  local y, m, d = lastRelease:match("(%d+)-(%d+)-(%d+)")
  local t = os.time({year = tonumber(y), month = tonumber(m), day = tonumber(d), hour = 12})
  t += intervalDays * 24 * 60 * 60
  return os.date("%Y-%m-%d", t)
end
```
`hour = 12` защищает от сдвигов из-за перехода на летнее время. (В Roblox `os.date` работает аналогично; для UTC используйте префикс `!` в формате.)
:::
